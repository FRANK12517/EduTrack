## Domain and relationship map evidenced by the migration runner

- **Identity and authorization:** `users` → `credentials`; `users` ↔ `roles` through `user_roles`; `roles` ↔ `permissions` through `role_permissions`; `server_sessions` and password-reset records reference user identities. Role and permission names are seeded in application code.
- **Organization scope:** `tenants.parent_id` self-references; `tenant_memberships` associates users and tenants; `districts.region_id` references regions; schools reference tenant/district; staff and students carry tenant/school scope.
- **School personnel and family:** staff-school, teacher-class, and teacher-subject assignment tables; students reference school/tenant/class; `parent_student_relationships` links parent users and students. Application authorization also checks memberships/assignments, so FKs alone do not prove RBAC isolation.
- **Academics and attendance:** academic configurations, subjects, classes, attendance registers/records, teacher attendance, examinations/components, scores, published results, report snapshots, broadsheets, and promotion records. Preserve school-year/term semantics and source identifiers; do not normalize or change key formats as part of driver conversion.
- **Finance:** payment intents, transactions/events, subscriptions, fee/payment tables, carry-forward records, population checkpoints and private-school year controls. Keep `DECIMAL` precision; no float conversion. Reconcile idempotency/unique keys and external Paystack references.
- **Communications, files and audit:** campaign/recipient, chat, file, signature, transport and audit-event tables. These may contain sensitive content or cross-tenant metadata and require explicit ownership policies.
- **Transport and hostel:** transport has migration-runner definitions; hostel table definitions appear only in `db/schema.sql`, despite application hostel functionality. Resolve the missing migration before claiming feature schema coverage.

These relationships are a source-code map, not an independently validated current database catalog. The migration source contains foreign keys for core user, tenant, school, academic, payment, quiz, transport and audit relations; validate every one and every implicit application relation against production before data movement.

## Identifier, type, nullability and index decisions

- Existing IDs are predominantly string IDs (`VARCHAR(80)` with application-generated prefixes), not `AUTO_INCREMENT`. Preserve exact values and every dependent FK. Do not replace them with UUID/identity columns without a separately approved data/API migration.
- Existing schema definitions use `TIMESTAMP`, `DATE`, `TIME`, `BOOLEAN`, `TINYINT`, `JSON`, `DECIMAL`, nullable and default clauses inconsistently across tables. Define a per-column mapping; use `timestamptz` only when the stored value represents a real instant and source timezone is known. Never assume current naive timestamps are UTC.
- `JSON` to `JSONB` is not mechanical: test key/value semantics, ordering assumptions, extraction expressions and indexes. Preserve money/grade precision with exact numeric types.
- DDL embeds MySQL `ENGINE=InnoDB`, inline `KEY`/`UNIQUE KEY`, and in some cases multiple MySQL `ALTER TABLE` actions. Catalogue unique indexes, composite order, partial predicates and FK delete/update actions before translating.
- No generated-column or auto-increment conversion can be inferred globally. Confirm each default and sequence requirement from actual data and code paths.
